First, the map

Three packages, one direction of data flow. Keep this picture in your head; every file below hangs off it.

main.goOwns everything. Tray icon, popup window, file picker, saved theme.
internal/playerPlays the file. Open, play, pause, seek, volume. Outlives the popup, so music keeps going.
internal/mixPure data. The 28 chapter names and their start times. No audio here.
owns ↓
reads ↓
searched by ↓
internal/viewDraws the popup. Rebuilt from scratch every frame. Holds no state of its own.

The word internal is a Go rule, not a naming choice: code under internal/ can only be imported by this repo. That is what keeps the layers from leaking into each other.

One sentence to remember: main owns state, player owns sound, mix owns facts, view draws. When something breaks, the symptom tells you the package.

Seven Go ideas, with real code

Each card is one idea, explained in plain words, with a snippet taken from this repo. Learn these and the whole codebase reads like plain text.

1 · Packages and imports

A package is a folder of code that goes together. The first line of every file names its package. import pulls in other packages, like require in Node.

package player

import (
    "time"
    "github.com/egoist/mygo/audio"
    "drift/internal/mix"
)
player/player.go, top of file

2 · Structs and methods

A struct is a group of fields. A method is a function attached to a struct. The part in brackets, (p *Player), is the receiver: which struct the method works on.

type Chapter struct {
    At     time.Duration
    Artist string
    Title  string
}

// Name is a method on a Chapter value.
func (c Chapter) Name() string {
    if c.Title == "" { return c.Artist }
    return c.Title
}
mix/tracks.go

The one rule that matters: (c Chapter) gets a copy; (p *Player) gets the real one and can change it. Data types like Chapter use value receivers. Working things like Player use pointer receivers.

3 · Pointers, just enough

&x means "the address of x". *T means "a pointer to a T". The view gets pointers to the app's state, so it always sees the live values, not old copies.

// Model holds pointers, so the view reads live state.
Scroll *ui.ScrollState
Angle  *float32
view/view.go

4 · Errors are values

Go has no exceptions here. Functions return an error next to their result. You check it with if err != nil. Once this pattern clicks, all Go code reads the same.

f, err := os.Open(path)
if err != nil {
    return fmt.Errorf("cannot open the recording: %w", err)
}
player/player.go, Open()

%w wraps the original error inside the new one, so the cause is never lost.

5 · Slices and maps

A slice is a list. A map is a lookup table. The 28 chapters are one slice; the icon lookup is a map.

// a slice of structs
var Chapters = []Chapter{
    {0, "Intro", ""},
    {15 * time.Second, "WYS", "Snowman"},
    ...
}

// a map: id in, glyph name out
glyph := map[string]string{
    "system": "auto",
    "light":  "sun",
    "dark":   "moon",
}[ids[i]]
mix/tracks.go and view/view.go

6 · Closures

Functions are values in Go. You can pass one to another function. MyGo builds every layout this way: you open an element, then hand it a function that fills its children.

ui.Column(c).Fill().Children(func() {
    header(c, t, m)
    plateSection(c, m, st)
    chapterList(c, t, m, st)
})
view/view.go, Screen()

7 · defer

defer runs a line when the function exits, no matter how it exits. Perfect for releasing locks or closing files.

func (p *Player) Volume() float64 {
    p.mu.Lock()
    defer p.mu.Unlock()  // runs on the way out
    return p.volume
}
player/player.go

8 · time.Duration

A length of time you can do maths on. Chapters are written as 205 * time.Second and the player compares them directly.

// duration maths, everywhere in this repo
{205 * time.Second, "Fatb", "Cotton Cloud"}
mix/tracks.go

The one concurrency idea you must not skip

Two things run at once in this app: the audio callback and the drawing of the window. Both touch the same Player. A mutex (a lock) makes them take turns.

The rule

In player.go, every read or write of the Player's fields happens between Lock() and Unlock(). One turn at a time, always.

func (p *Player) State() State {
    p.mu.Lock()
    s, total, path := p.stream, p.total, p.path
    p.mu.Unlock()

    pos := s.Position()
    return State{ Loaded: true,
        Playing: s.Playing(), ... }
}
lock on the way in, released on the way out

What happens if you skip it

One day you "clean up" a lock away. The app then crashes in a way that looks random. That crash is called a data race: two things writing one value at the same moment.

Go can find these for you. Run go test -race ./... and it names the two lines that collided.

Self-check: open player.go and find Close(). Notice it copies the fields out under the lock, then closes them after the lock. Ask yourself why. (Answer: closing a stream can take time; you never hold a lock during slow work.)

The UI mindset: it is drawn fresh every frame

MyGo is not like React. There are no components that remember things. The whole popup is rebuilt from scratch, many times a second, from your data.

Why app.model() exists

Every frame, main hands the view a fresh bundle of the current state and the callbacks.

Why scroll and angle live in main.go

The view forgets everything between frames. Only state stored outside survives, so main keeps it and passes it in as pointers.

Why an unbounded list never scrolls

Each frame, a list asks its content how tall it is. If nothing bounds its height, it grows as tall as its content. Nothing is left to scroll. That is why the code sets an explicit height.

Why animation uses el.Loop

Loop tells the engine "keep sending me frames". A manual repaint request fights the engine, rebuilds everything, and stutters.

// the disc: one loop, 12 seconds per turn, 0..1 progress * 360
if st.Playing && !c.Preferences().ReduceMotion {
    angle = el.Loop("turn", 12*time.Second, ui.Linear) * 360
}

The reading order

Five files, smallest to biggest idea. Do them in this order; each one prepares you for the next.

  1. mix/tracks.go

    95 lines, pure Go, no framework. Structs, slices, a binary search. Finish this and ideas 1, 2, 5 and 8 are yours.

  2. view/theme.go

    34 lines. Your first look at the ui package. It also explains why the light blue is darker than the dark blue: contrast rules.

  3. player/player.go

    Errors, locks, callbacks. This is where Go starts feeling like Go.

  1. main.go

    How the pieces get wired: tray, popup, file picker, saved theme. Notice how little it does itself. It connects things.

  2. view/view.go

    Immediate-mode UI in full. Read this last, after the mindset section above.

Then skim the tests: player_test.go and screen_test.go. Tests show what the code is supposed to do, better than comments do.

cd desktop
go test ./...

Test before and after every change

Two commands cover it. The first runs the unit tests. The second adds the real recording.

Unit tests

Fast, no audio file needed. Run them first.

cd desktop
go test ./...

With the real recording

Point DRIFT_MIX at your mp3. The streaming and chapter tests then use it.

# PowerShell
$env:DRIFT_MIX = "C:\path\to\your-mix.mp3"
go test ./...

If a test fails after your change, the test name names the behaviour that broke. Trust it before you trust a build that looks fine.
